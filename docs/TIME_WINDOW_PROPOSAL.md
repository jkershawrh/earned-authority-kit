# Explicit demo blackout — implementation and scope

The user selected an explicitly configured demo blackout and left the real business policy open. [Live008](../reports/service-bdd-live-008.json) completes BDD-009 for this configured demo using the actual Foundation/OPA services; component tests alone would not establish that acceptance.

The canonical Foundation Rego source defines `demo-2100-01-01-first-minute`: `[4102444800000, 4102444860000)` UTC epoch milliseconds, or 2100-01-01 00:00:00–00:01:00 UTC. This finite example is operator configuration in pinned source, not an invented recurring business calendar. A reviewed source change, digest repin and immutable OPA snapshot restart are required to change it. The existing policy digest therefore binds both the rule and its configured interval.

The policy request optionally includes `requested_window` with exactly two integer fields, `not_before_ms` and `not_after_ms`. Bounds satisfy `0 <= start < end <= 2^53-1`. The start is included and the end is excluded. Actual OPA server time supplies immediate-check time; caller clocks and calendar fields are not consumed. The decision binds the exact interval and engine evaluation time to the existing request and policy identity. Any interval overlap denies model promotion with `POLICY_WINDOW_DENIED`; current time inside the blackout also denies unwindowed promotion. Other actions retain their existing rules. Unsupported windowed actions and legacy stub routes fail closed.

The reference coordinator verifies the subject, policy, interval and integer evaluation-time bindings before trusting this denial reason. An eligible qualification remains eligible after policy denial, and no credential or registry mutation is created. For an allowed interval, `grant(..., requested_window=...)` requires that the local current time is already inside it, caps scope expiry at the interval end, and includes the interval in the signed grant and durable operation request. Preflight and mutation checks revalidate it. It does not schedule a future grant. Retrying an already applied authority operation returns current authority without issuing another credential; historical receipts never restore expired permission.

Canonical component tests cover malformed intervals, clock spoofing, overlap equality, otherwise-permitted resources, unchanged unrelated actions, exact response binding and unsupported routes. Python unit tests cover denial without authority, future-start refusal, expiry caps, signed window binding, preflight timing, expiry of a PREPARED operation before recovery, a policy call crossing the execution deadline, and durable retry identity. Existing generic journal expiry and historical-receipt tests cover the same capped expiry field; they are not additional window-specific live scenarios. Controlled clock overrides are confined to tests; connected acceptance uses actual OPA and coordinator clocks. Live acceptance, deployments and production business-calendar suitability must be assessed separately.

The single-host reference trusts its local system clocks. The consumer checks the OPA evaluation timestamp's type/range and its decision binding; it does not prove cross-host clock synchronization or clock monotonicity. These checks are not a distributed scheduling or time-authority guarantee.
